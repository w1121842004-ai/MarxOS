# MarxOS 开发日志

## 日期

2026-05-11

## 1. 今日目标

今天的核心目标是把 MarxOS 从“单本或少量文档可检索的 OCR-RAG 原型”推进到“可覆盖《马克思恩格斯全集》主体卷册的大规模学术知识库”。

具体目标包括：

- 复用已有 OCR 缓存，避免重复 OCR 带来的高耗时。
- 批量构建 `marx_knowledge_base` FAISS 向量库。
- 为检索结果补充更稳定的 metadata，包括书名、卷号、PDF 页码、印刷页码、篇目或章节信息。
- 让前端入口 `app.py` 能识别不同问题类型，例如篇目定位、引文查找、概念解释和理论分析。
- 改善引用格式，使回答更接近学术脚注，而不是只暴露内部检索来源。

## 2. 今日遇到的问题

### 2.1 OCR 缓存规模变大后，重建知识库耗时明显上升

今天知识库构建不再只处理少量测试文本，而是开始面向大规模 OCR 缓存。当前 `data/ocr_cache` 下已经有 61 个缓存目录、42737 个 OCR 文本页。

直接从 PDF 重新 OCR 会非常慢，而且容易在中途因为单页识别失败、环境波动或进程中断造成整体重跑。因此今天将构建流程调整为：

```text
OCR cache txt
-> Document(metadata)
-> chunk
-> embedding batch
-> FAISS
```

这样可以把 OCR 阶段和向量库构建阶段解耦，后续只要缓存存在，就可以直接重建向量库。

### 2.2 全量文档直接构建会带来内存与进度不可见问题

缓存页数量很大，如果一次性全部 embedding，不仅耗时长，而且出问题时很难判断当前进度。今天在 `rag/build_vectorstore_from_cache.py` 中加入了批量 embedding 和进度输出：

- `BATCH_SIZE` 控制 embedding 批大小，默认 1024。
- `READ_PROGRESS_EVERY` 控制 OCR 缓存读取进度输出。
- `SPLIT_PROGRESS_EVERY` 控制 chunk 切分进度输出。
- 构建时先写入临时目录，完成后再替换正式向量库目录。

最终日志显示，本轮构建完成了：

```text
136592 chunks
vectorstore/marx_knowledge_base 构建完成
```

### 2.3 《资本论》和全集卷册混建时，测试范围不够可控

构建过程中发现不同来源文档混在一起会影响调试效率。尤其是《资本论》已经有单独缓存和历史测试结果，而今天重点是《马克思恩格斯全集》主体卷册。

因此新增了构建过滤参数：

```text
ME_VOLUMES_ONLY=1
SKIP_PDFS=capital.pdf
```

这样可以先集中构建 `me01.pdf` 到 `me50.pdf` 这类全集主体卷，跳过 `capital.pdf`，避免调试目标发散。

### 2.4 页码 metadata 不稳定，容易把年份、注释号或水印误判成页码

OCR 文本中经常出现这些干扰：

- 出版年份，例如 1979、2004、2009。
- 页脚倒序识别。
- PDF 水印、下载站标记。
- 目录页、正文页、索引页格式不同。
- OCR 把页码附近的章节名和正文混在一起。

这会导致 RAG 引用时出现错误页码，或者把 PDF 页码误当成印刷页码。

今天在 `rag/build_vectorstore_from_cache.py` 中补充了页码推断逻辑：

- `normalize_digits()` 统一处理全角数字。
- `strip_pdf_boilerplate()` 去除 PDF 水印和下载站噪声。
- `is_valid_printed_page()` 排除明显不合理页码和年份。
- `is_plausible_for_pdf_page()` 判断印刷页码与 PDF 页码的偏移是否合理。
- `infer_reversed_footer_page()` 尝试识别 OCR 倒序页脚。
- `infer_page_metadata()` 从页首和页尾扫描候选页码。

现在 metadata 同时保留：

```json
{
  "page": "优先使用印刷页码，否则回退到 PDF 页码",
  "printed_page": "识别到的印刷页码",
  "pdf_page": "OCR 缓存页码",
  "source": "来源 PDF",
  "ocr": true
}
```

### 2.5 篇目定位仅靠向量检索不稳定

用户如果问“《反杜林论》在哪一卷”“《自然辩证法》从哪一页开始”，这类问题本质上是书目定位，不应该完全依赖语义相似度。单靠 embedding 会出现以下问题：

- 检索命中正文片段，而不是目录条目。
- 篇名和正文理论概念相似时，容易命中错误卷。
- 页码范围难以稳定输出。

因此今天新增了目录与篇目映射能力：

- `rag/extract_article_map.py`：用于读取 OCR 缓存前若干页，辅助观察目录文本。
- `rag/generate_article_map.py`：从 PDF 目录页抽取篇目、起始页、结束页。
- `rag/article_map.json`：保存篇目映射结果。

当前 `article_map.json` 覆盖 60 个来源文件，共抽取 9155 条目录/篇目信息。

### 2.6 向量库已生成后，metadata 仍需要二次修复

在知识库构建完成后，发现已有 `index.pkl` 中部分 chunk 的 metadata 仍然需要重新从 OCR 缓存推断，以补齐或修正：

- `book`
- `article`
- `chapter`
- `section`
- `page`
- `printed_page`
- `pdf_page`

为此新增了 `rag/repair_vectorstore_metadata.py`。该脚本会：

1. 读取 `vectorstore/marx_knowledge_base/index.pkl`。
2. 根据每个 chunk 的 `source` 和 `pdf_page` 回到 OCR 缓存找原始文本。
3. 重新推断印刷页码和篇目信息。
4. 写回 metadata。
5. 首次执行时备份为 `index.pkl.bak`。

这一步降低了重建整个 FAISS 的成本，也让后续 metadata 修复可以独立进行。

### 2.7 回答入口缺少问题意图分类，导致不同问题被同一种 prompt 处理

原先 `app.py` 更像一个通用 RAG 入口，不区分用户到底是在问：

- 某篇文章收录在哪一卷。
- 某句话出自哪一页。
- 某个概念是什么意思。
- 某个现实问题如何用马克思主义理论分析。

今天在 `app.py` 中加入了 query intent 分类：

```text
bibliographic_lookup
quote_lookup
concept_explain
theory_analysis
rag_answer
```

并为不同意图构造不同 prompt。这样做的结果是：

- 书目定位类问题可以优先走目录映射，不必调用 LLM 做长篇解释。
- 引文查找类问题要求只输出出处，避免不必要理论分析。
- 概念解释类问题要求先定义，再说明理论位置。
- 理论分析类问题才展开结构化论述。

### 2.8 引用格式需要从“内部检索信息”升级为“学术可读格式”

之前回答容易暴露内部字段，例如：

```text
资料1
PDF第X页
source: me46a.pdf
```

这对调试有用，但不适合作为面向用户的学术回答。今天在 `app.py` 中加入了引用格式化逻辑：

- `normalize_book_parts()` 负责从 metadata 中整理作者、书名、卷号、出版年份。
- `format_citation()` 输出句子级或段落级出处。
- `MARXOS_DEBUG_SOURCES=1` 时才额外输出内部检索来源。

这样默认回答更接近：

```text
《马克思恩格斯全集》第X卷，北京：人民出版社，出版年不详，第X页。
```

而不是直接展示向量库内部字段。

后续无需每次从 PDF 重新 OCR，可以直接从缓存进行：

### 4.3 篇目映射初步可用

```text

```

这为后续回答“某篇文章在哪一卷、哪几页”提供了结构化依据。

### 4.4 检索链路从单纯相似度搜索升级为带约束检索

现在系统不再只做：

```text
query -> similarity_search -> LLM
```

而是变为：

```text
query
-> intent classify
-> article map constraints
-> similarity_search
-> metadata rerank
-> prompt by intent
-> DeepSeek answer
```

这让系统更接近 Academic RAG，而不是普通聊天机器人。

### 4.5 引文输出更加学术化

系统现在可以在 context 中为模型提供两种出处格式：

- 句子引用格式。
- 段落具体出处格式。

并要求模型优先使用这些格式输出，减少 PDF 页码、source 文件名等内部信息直接暴露给用户的概率。

## 5. 当前遗留问题

### 5.1 终端显示仍存在编码错显

部分文件在当前 PowerShell 输出中会显示为乱码，但通过 Python 读取样本 metadata 可以看到实际数据中已有正常中文，例如：

```python
{
  "book": "马克思恩格斯全集 第1卷",
  "source": "me01.pdf",
  "ocr": True
}
```

后续需要统一检查：

- 文件本身是否全部为 UTF-8。
- PowerShell 控制台编码是否为 UTF-8。
- 旧文件是否曾经以错误编码保存。

### 5.2 部分 metadata 仍可能不够精确

虽然今天已经增加页码推断和篇目映射，但 OCR 文本复杂，仍可能存在：

- 印刷页码识别失败。
- 目录条目被 OCR 错读。
- 篇目跨页范围不准确。
- `section` 为空或落到过宽范围。

后续需要通过典型问题集进行抽样验证。

### 5.3 目录抽取仍依赖启发式规则

`generate_article_map.py` 当前主要依赖目录页特征、页码模式和文本行清洗。对于特殊目录、跨行标题、OCR 错乱严重的卷册，仍可能漏抽或误抽。

后续可以考虑：

- 针对全集卷册建立人工校正表。
- 将目录识别结果导出为可审校格式。
- 为重要著作单独维护高可信篇目映射。

### 5.4 app.py 逻辑已经变重，后续需要模块化

今天为了快速打通检索、分类、引用和书目定位，很多逻辑集中在 `app.py` 中。短期便于验证，但长期会影响维护。

后续建议拆分为：

```text
rag/query_intent.py
rag/citation.py
rag/article_lookup.py
rag/retriever.py
rag/prompt_builder.py
```

## 7. 今日总结

今天 MarxOS 的主要进展，是完成了从“小规模 OCR-RAG 原型”到“大规模全集知识库”的关键过渡。

系统已经具备：

- 复用 OCR 缓存构建知识库的能力。
- 13 万级 chunk 的 FAISS 向量库。
- 面向全集卷册的目录/篇目映射。
- metadata 二次修复能力。
- 根据问题意图切换回答策略的入口逻辑。
- 更接近学术引用格式的出处输出。

今天的问题主要集中在数据工程层面：规模、页码、篇目、编码和 metadata。解决这些问题后，MarxOS 的核心不再只是“能检索”，而是开始具备“可引用、可定位、可扩展、可校正”的学术知识系统雏形。
