# MarxOS 高频面试题答案 30 题

> 这份文档按照“面试最容易追问、最能体现项目含金量”的顺序组织。回答重点不是背概念，而是讲清楚：遇到了什么真实问题、为什么这样设计、做了什么工程取舍、怎么验证效果。

## 1. 你这个项目到底解决了什么问题？为什么它不是一个普通的 RAG 问答 Demo？

MarxOS 解决的是马克思主义经典文本的本地学术问答问题，核心目标不是简单“问一句答一句”，而是让回答能回到原文、篇名和页码，用户可以核对依据。

普通 RAG Demo 往往只做三件事：切 chunk、向量检索、把结果塞给大模型生成回答。但 MarxOS 面向的是《马克思恩格斯全集/文集/选集》这类严肃文本，用户关心的不只是答案流畅，而是出处是否准确、页码是否可信、是否引用了正确版本、是否把相似篇目混在一起。

所以这个项目在普通 RAG 之外做了很多工程增强：

- 从 PDF 到 OCR 缓存，再到段落缓存和向量库的完整数据管线。
- 支持 Dense + BM25 混合检索，不只依赖语义向量。
- 支持小块检索、父段落窗口扩展，兼顾召回精度和上下文完整性。
- 有 WorkCatalog、article map、locator 等结构化元数据，用来约束篇名、版本和页码。
- 有 CRAG 检索质量评分和纠正性重检索。
- 有引用格式修复、引用审计和 OCR 内容验证。
- 有 fast、standard、deep 不同性能模式，兼顾速度和质量。

所以我会把它定义为“面向经典文本的可信 RAG 系统”，而不是一个简单的聊天式 RAG Demo。

## 2. MarxOS 面向的是马克思恩格斯经典文本，这类学术语料和普通网页知识库相比，最大的技术难点是什么？

最大的难点是：答案必须可考证，而且语料本身结构复杂。

普通网页问答里，只要答案大体正确，用户可能就能接受。但经典文本问答不同，用户经常会问“这句话出自哪里”“某篇文章在哪一卷哪一页”“某概念在原文中怎么表述”。这要求系统不仅能生成解释，还要能定位到具体著作、版本、页码和引文。

这类语料有几个特殊难点：

- PDF 页码和印刷页码不一致，直接引用 PDF 页会误导用户。
- OCR 会产生乱码、页眉页脚、页码噪声，影响检索和引用。
- 同一篇文章可能出现在《全集》《文集》《选集》多个版本中，页码不同。
- 篇名、别名、简称很多，比如用户可能不输入完整书名。
- 理论概念存在跨篇章表达，不能只靠单个 chunk。
- 引文定位要求非常高，不能把相似句子当成原文出处。

所以这个项目的难点不是“能不能调用 LLM”，而是如何把 OCR、页码、版本、检索、生成和审计串成一套可信链路。

## 3. 整个系统从 PDF 原文到最终带出处回答，中间完整链路是怎样的？

可以分成离线构建和在线问答两条链路。

离线构建阶段：

1. 输入原始 PDF，包括《全集》《文集》《选集》等卷册。
2. 使用 OCR 将 PDF 页面转换成文本缓存。
3. 对 OCR 文本做清洗，包括乱码修复、页码识别、页眉页脚处理。
4. 从页面文本中切分段落，生成 paragraph cache。
5. 将段落切成较小的 semantic child chunk，写入 `parent_paragraph_id`。
6. 使用 BGE-M3 生成 embedding。
7. 构建 Milvus 或 FAISS 向量库。
8. 同时构建 WorkCatalog、article map、page map、locator 等结构化元数据。

在线问答阶段：

1. 用户通过 Web 或 CLI 提问。
2. 系统识别 query 意图，比如书目查找、引文定位、概念解释、理论分析等。
3. 根据意图构建检索约束，比如篇名、版本、页码范围、主题词。
4. 执行 Dense/BM25/Hybrid 检索。
5. 对命中的小块做父段落窗口扩展，补足上下文。
6. 对检索结果做重排序、去重、多样化和质量评分。
7. 如果质量不够，触发 CRAG 纠正性重检索。
8. 构造 evidence cards 和 prompt，调用 DeepSeek 生成回答。
9. 对回答中的引用做格式修复和引用审计。
10. deep 模式下进一步用 OCR 原文验证引用内容。
11. 返回带出处、篇名、页码和证据卡的回答。

这个链路的核心是：先把文本资产做干净，再让检索带约束，最后让生成结果可审计。

## 4. 为什么这个项目特别强调“可核对引用”和“页码准确”？

因为 MarxOS 的使用场景更接近学术检索和理论学习，而不是泛泛聊天。

如果用户问“异化劳动是什么意思”，系统可以解释。但如果用户继续问“原文在哪里”，或者“这句话出自哪一卷哪一页”，系统必须给出可核对的出处。否则即使答案看起来流畅，也没有学术可信度。

页码错误会带来很严重的问题：

- 用户无法回到原文核对。
- 系统可能把不同版本的内容混在一起。
- LLM 可能生成看似合理但不存在的引用。
- 对学术写作、教学、研究场景来说，错误出处比没有出处更危险。

所以项目里不只做“生成答案”，还做了页码映射、引用格式修复、引用审计、OCR 内容验证等环节。目标是让回答能被追溯，而不是只让回答听起来合理。

## 5. 你们是如何处理 PDF 页码和印刷页码不一致的问题的？

项目采用多层页码解析策略。

第一层是人工或半自动构建的 `page_map.json`。它记录 PDF 页码到印刷页码之间的映射关系。对于核心卷册和高频篇目，这是最可靠的方式。

第二层是 OCR 缓存边缘检测。很多扫描书页会在页面顶部或底部保留印刷页码，所以系统会读取每页 OCR 文本的前几行和后几行，用正则寻找独立数字行，再结合合理偏移范围判断它是不是印刷页码。

第三层是元数据归一化。在检索和引用输出阶段，系统会统一处理 `pdf_page`、`printed_page`、`citation_page` 等字段，回答时优先使用印刷页码。

这样做的原因是：PDF 第 1 页可能是封面、版权页、目录，而不是书籍正文第 1 页。如果直接引用 PDF 页码，用户查书时会找不到对应内容。

## 6. OCR 乱码、页眉页脚、页码噪声会怎么影响检索质量？项目里是怎么清洗和修复的？

OCR 质量会直接影响 RAG 的上游数据质量。如果 OCR 文本里有乱码、页眉页脚、重复页码或断裂句子，embedding 会被污染，BM25 也会匹配到无意义词，最终导致召回不准。

项目里遇到过典型 mojibake 乱码，比如 UTF-8 字节被错误解释成 Latin-1，中文会变成类似 `é©¬å...` 的字符。这类乱码如果不修复，向量模型无法正确理解，检索质量会明显下降。

处理方式包括：

- 对疑似乱码字符做标记检测，正常文本走快速路径。
- 对疑似乱码片段做 Latin-1 到 UTF-8 的反向解码。
- 解码失败就保留原文，避免引入新错误。
- 对 OCR 文本做页码、页眉页脚和空白噪声清理。
- 在段落构建阶段过滤过短、非正文或定位提示型文本。

这里的经验是：RAG 的质量很大程度取决于数据层，不是换更大的 LLM 就能解决 OCR 噪声问题。

## 7. 为什么采用“小块检索 + 父段落窗口扩展”的方案？

这是为了解决 RAG 中“小块精准”和“大块完整”之间的矛盾。

如果 chunk 太小，比如 180 个字符，embedding 的语义会比较集中，适合精准召回。但问题是上下文不足，LLM 可能看不懂前后逻辑。

如果 chunk 太大，比如整个段落甚至多段一起做 embedding，上下文完整了，但语义会被稀释。一个大段落里可能同时讲多个概念，向量检索时不一定能精确命中用户问题。

所以项目采用两阶段设计：

- 索引时，把完整段落切成小块，每个小块带上 `parent_paragraph_id`。
- 检索时，先用小块做精确语义召回。
- 命中后，根据 `parent_paragraph_id` 找回父段落，并扩展前后段落作为上下文。

这样既保留了小块 embedding 的召回精度，又给 LLM 足够的上下文来生成可靠回答。

## 8. 什么是 `parent_paragraph_id`？为什么早期向量库缺少这个字段会导致检索质量静默下降？

`parent_paragraph_id` 是子块和原始段落之间的关联字段。

因为系统检索的是小块，但生成回答时需要更完整的段落上下文，所以必须知道每个小块来自哪个父段落。只有这样，命中小块后才能回查完整段落，并扩展前后段落。

早期向量库缺少这个字段时，系统表面上仍然能检索到结果，但父段落扩展无法执行。这样不会一定报错，而是静默退化成只使用小块上下文。

这种问题很隐蔽，因为系统还能返回答案，但答案质量会下降：

- 上下文不足。
- 引用容易断章取义。
- LLM 更容易补充幻觉内容。
- 深度分析类问题尤其受影响。

这个问题的教训是：RAG 向量库不只是文本和 embedding，元数据 schema 同样关键。构建阶段必须做字段校验，不能等线上质量下降才发现。

## 9. 为什么要同时构建子块向量库和段落向量库？

子块向量库和段落向量库解决的是不同问题。

子块向量库适合精准召回。它的 chunk 比较短，embedding 更聚焦，适合找到和用户 query 最接近的局部文本。

段落向量库适合补充上下文和提高覆盖。完整段落保留了更完整的语义结构，适合理论分析、概念解释、跨句表达等问题。

在实际检索中，系统可以先用子块找精确锚点，再用段落检索补充更多上下文。deep 模式下还可以启用段落双路检索，让回答获得更稳定的证据来源。

这种设计比单一粒度更灵活：

- 精确引文定位更依赖小块。
- 理论解释更依赖完整段落。
- 深度分析需要多段证据组合。

所以双粒度索引是为了适配不同查询意图，而不是重复建设。

## 10. 为什么项目里要做 Dense + BM25 的混合检索？单纯向量检索不够吗？

单纯向量检索适合语义相似问题，但在经典文本问答中不够。

向量检索的优势是能理解近义表达，比如用户问“异化劳动的含义”，即使原文不完全这么写，也可能召回相关段落。但它的短板是对精确词、篇名、人名、固定引文、页码线索不够稳定。

BM25 的优势正好相反。它基于关键词匹配，对精确短语、书名、引文片段、专有名词更敏感。

例如：

- 用户输入一段原文找出处，BM25 很可能比向量检索更准。
- 用户问某个篇名在哪一卷，关键词和 locator 约束很重要。
- 用户输入冷门术语，embedding 可能语义漂移，BM25 能保留字面命中。

所以项目做 Dense + BM25 混合检索，用 Dense 负责语义泛化，用 BM25 负责精确匹配。融合后整体召回更稳。

## 11. BM25 在这个项目里主要补齐了向量检索的哪些短板？

BM25 主要补齐三个短板。

第一是精确引文。用户输入一段原文或半句原文时，字面重合度非常重要，BM25 往往能直接命中原段落。

第二是专名和篇名。很多马克思主义经典著作篇名较长，向量检索可能只理解大概语义，但 BM25 能抓住关键词。

第三是低频术语。某些概念或人名在 embedding 空间中不一定有很好的表示，BM25 通过词项匹配可以避免语义漂移。

当然 BM25 也有不足，比如无法很好处理同义改写，所以它不是替代 Dense，而是和 Dense 互补。

## 12. 混合检索结果如何融合和排序？为什么需要 RRF 或类似的融合策略？

Dense 和 BM25 的分数体系不同，不能简单相加。

Dense 通常是向量相似度，BM25 是词项相关性分数，两者数值范围和含义都不同。如果直接相加，某一路分数可能会支配结果，导致融合失衡。

RRF，也就是 Reciprocal Rank Fusion，更关注排名而不是原始分数。它根据文档在不同检索器中的名次进行融合：一个文档如果在 Dense 和 BM25 中都排名靠前，就会得到更高融合分。

这种方式的好处是：

- 不依赖不同模型分数的绝对尺度。
- 对多路检索结果更稳定。
- 能提升同时被语义和关键词命中的文档。
- 避免单一路检索异常支配最终结果。

在 MarxOS 这种场景里，RRF 能让“语义相关”和“字面匹配”同时发挥作用。

## 13. Milvus 和 FAISS 在项目里分别承担什么角色？为什么不是只保留一个向量库？

Milvus Lite 是当前主检索后端，FAISS 是离线和 fallback 后端。

Milvus 的优势是更像生产环境的向量数据库，有明确的 collection、schema、索引配置和过滤能力，适合承载更大规模、更结构化的检索。项目里主力使用 BGE-M3，向量维度 1024，Milvus 可以配合 HNSW 和 COSINE 做高效检索，也更适合后续混合检索和元数据过滤。

FAISS 的优势是轻量、离线可用、依赖少，适合本地 fallback 和早期构建。即使 Milvus 环境不可用，系统仍然可以通过 FAISS 跑起来。

保留两者是工程取舍：

- Milvus 面向主线能力和扩展。
- FAISS 保证离线可用和兼容历史索引。
- VectorBackend 抽象可以屏蔽底层差异，方便切换。

这比强行只保留一个后端更稳，尤其是在本地研究项目和准生产系统之间过渡时。

## 14. 为什么主检索后端迁移到 Milvus Lite？

迁移到 Milvus Lite 主要是为了让检索后端更接近生产形态。

FAISS 本身很强，但它更像一个向量索引库。随着项目规模扩大，需要更多结构化能力，比如 schema 管理、元数据字段、过滤、collection 管理、索引参数配置和后续混合检索扩展。

Milvus Lite 的优势是：

- 本地即可运行，不需要完整分布式 Milvus 集群。
- 支持更明确的 collection schema。
- 适合管理 BGE-M3 这类高维向量。
- 支持 HNSW + COSINE 等检索配置。
- 未来迁移到 Milvus 服务版更平滑。

所以它是一个兼顾本地开发和生产演进的选择。

## 15. BGE-M3 为什么适合这个项目？

BGE-M3 适合这个项目主要有三个原因。

第一，它对中文语义检索支持较好。MarxOS 的语料是中文经典文本，embedding 模型必须能处理中文理论概念、长句和专有表达。

第二，它支持更强的语义表达能力。相比 MiniLM 这类轻量模型，BGE-M3 的向量维度和表达能力更强，适合学术文本这种复杂语义场景。

第三，它可以支持 dense 和 sparse 相关能力，适合后续混合检索扩展。

当然 BGE-M3 的代价是模型更大、推理更慢、资源占用更高。所以项目里仍然保留轻量 fallback 和性能模式，避免所有场景都被高成本模型绑定。

## 16. 查询意图识别为什么要单独做？为什么不能所有问题都走同一套 RAG prompt？

因为不同问题需要不同检索策略和回答策略。

例如用户问“《关于费尔巴哈的提纲》在哪一卷”，这是书目查找问题，应该优先走 WorkCatalog 和 locator，而不是盲目向量检索。

用户问“这句话出自哪里”，这是引文定位问题，应该更重视精确匹配、BM25 和 OCR 原文验证。

用户问“异化劳动是什么意思”，这是概念解释问题，需要召回多个相关段落，并生成解释型回答。

用户问“比较异化劳动和剩余价值”，这是比较分析，需要多主题证据和更大的上下文。

如果所有问题都走同一套 RAG prompt，会出现：

- 检索策略不匹配。
- 书目类问题被当成普通问答。
- 引文定位不够精确。
- 深度分析上下文不足。
- prompt 过大且不聚焦。

所以意图识别是整个系统的路由器，它决定后续检索、约束、prompt 和回答风格。

## 17. MarxOS 里的 7 类查询意图分别解决什么问题？

可以概括为七类。

第一类是书目查找，比如“《德意志意识形态》在哪一卷”。重点是定位著作、版本、卷册和页码范围。

第二类是引文定位，比如“这句话出自哪里”。重点是精确匹配原文和给出可靠出处。

第三类是概念解释，比如“什么是异化劳动”。重点是召回相关段落，并用通俗但忠实原文的方式解释。

第四类是比较分析，比如“异化劳动和剩余价值有什么区别”。重点是分别召回两个概念的证据，再组织比较。

第五类是深度分析，比如“用马克思主义分析某个现实问题”。重点是检索理论依据，并结合问题做分析。

第六类是理论分析，比如“如何理解历史唯物主义”。重点是系统性解释理论脉络。

第七类是通用 RAG 问答，作为兜底处理其他可回答问题。

这些意图的区别不是标签好看，而是后续检索策略、prompt、上下文预算和引用要求都不同。

## 18. 意图识别为什么从“硬规则级联”演进到“并行打分 + 概率分布”？

硬规则级联的问题是，一旦前面的规则命中，就直接返回结果，后面的可能性没有机会参与判断。

例如一个问题可能同时像引文定位和概念解释。如果用硬优先级，系统可能因为某个关键词提前命中而走错链路。

并行打分的方式会让多个 scorer 同时评估 query，每类意图都得到一个 0 到 1 的分数，再归一化为概率分布。这样系统可以看到 top1、top2 的差距。

它带来的好处是：

- 能处理意图歧义。
- 置信度更可解释。
- 可以检测 ambiguous query。
- 后续可以融合 ML 分类器。
- 调试时能看到每类意图为什么得分。

这说明项目不是只写几个 if else，而是在逐步工程化意图路由。

## 19. 为什么项目里还尝试规则 + ML 混合意图分类？

纯规则的优点是可解释、可控、冷启动容易；缺点是泛化差，遇到新表达容易漏判。

纯 ML 的优点是泛化更好；缺点是需要训练数据，而且在数据不足时可能不稳定，也不如规则容易解释。

所以项目采用混合思路：规则 scorer 提供稳定基础，ML 分类器基于 BGE-M3 embedding 和 LogisticRegression 提供泛化补充。最终可以按权重融合，例如规则占一部分，ML 概率占一部分。

这种设计的好处是：

- 模型文件不存在时可以自动降级为纯规则。
- 有训练数据时可以提升泛化能力。
- 规则仍然保留业务边界。
- 结果比单一路径更稳。

这是一种比较务实的工程方案，适合数据逐步积累的项目。

## 20. WorkCatalog、article map、locator 这些结构化元数据在检索中起什么作用？

这些结构化元数据相当于 RAG 系统的“目录和索引”。

单纯向量检索只能根据语义相似度找文本，但很多问题其实需要精确定位。比如用户问某篇文章在哪一卷，最可靠的不是向量检索，而是查结构化目录。

WorkCatalog 记录著作标题、别名、版本、来源文件、起止页码等信息。article map 和 locator 则帮助系统把用户 query 中的篇名、别名或引文线索映射到具体篇目和页码范围。

它们的作用包括：

- 识别用户提到的著作。
- 处理简称、别名和不同译名。
- 给检索加上篇目和页码约束。
- 处理全集、文集、选集多版本问题。
- 在回答中输出可靠的书目信息。

所以结构化元数据不是辅助材料，而是提升可信度和精确定位能力的核心资产。

## 21. 多版本语料中，同一篇文章可能出现在《全集》《文集》《选集》中，系统如何处理版本优先级？

系统需要同时满足两个原则：默认权威优先，以及尊重用户指定。

默认情况下，如果用户没有指定版本，系统会按照预设优先级选择更权威或更完整的版本，比如优先《全集》。这是为了避免同一篇文章在多个版本中重复出现时，检索结果混乱。

但如果用户明确说“文集第几卷”或“选集里的版本”，系统就应该尊重用户约束，优先返回对应版本，而不是强行返回默认版本。

实现上，项目会通过 source、collection、work_catalog、locator 等字段判断来源，并在排序时加入版本优先级。用户 query 中如果出现版本约束，会覆盖默认优先级。

这类设计很重要，因为经典文本项目里，版本不同意味着页码不同，甚至编排和译文也可能有差异。

## 22. 什么是 CRAG 自修复？项目里为什么要在检索后做质量评分和纠正性重检索？

CRAG 可以理解为 Corrective RAG，也就是先评估检索结果质量，如果质量不够，就纠正检索策略并重新检索。

普通 RAG 经常有一个问题：只要检索器返回 top-k，系统就直接生成。但“有结果”不代表“结果可用”。一些结果可能没有页码、来源不对、篇名不匹配、只是目录提示，或者和 query 只有弱相关。

项目里会对检索结果做质量评分。如果分数低于阈值，就触发纠正性重检索，比如扩大 top-k、使用不同路由、加强标题约束、做 text overlap 过滤等。

CRAG 的价值是把 RAG 从“一次检索直接生成”升级成“检索后先自检，不合格再修复”。这对学术问答特别重要，因为低质量证据会直接导致错误引用和幻觉回答。

## 23. 检索质量评分主要看哪些维度？为什么“有结果”不等于“结果可用于生成回答”？

检索质量评分会看多个维度，而不是只看返回数量。

典型维度包括：

- 文档数量是否足够。
- 是否有明确页码锚点。
- match_type 是否可靠。
- 来源是否符合用户指定版本或默认优先级。
- 是否命中严格标题约束。
- 结果是否都是目录、前言、定位提示等非正文内容。
- 来源是否过于单一或过于发散。
- 片段文本和 query 是否有足够 overlap。

“有结果”不等于“可用于回答”，因为向量检索总能返回一些相似内容，但这些内容可能并不能支撑结论。尤其是 LLM 会倾向于根据不充分证据生成流畅答案，所以必须在生成前评估证据质量。

## 24. 引文审计是怎么做的？为什么 LLM 生成回答后还要再检查引用？

引文审计是对 LLM 输出的二次质量控制。

LLM 即使拿到了 evidence cards，也可能出现引用格式不规范、引用编号错乱、页码混用、把多个证据糅合成一个出处等问题。

项目中的引用审计通常包括：

- 检查回答中是否出现引用编号。
- 检查引用编号是否能对应到 evidence card。
- 修复书名、页码、编号等格式。
- 过滤回答中没有实际使用的证据。
- deep 模式下进一步验证引用内容是否真的存在于 OCR 原文中。

这一步的意义是：生成模型不是最终裁判。RAG 系统要对生成结果做后验检查，尤其是涉及出处和页码时。

## 25. OCR 内容验证为什么重要？它和普通 citation 格式检查有什么区别？

普通 citation 格式检查只看引用“长得对不对”，比如有没有编号、有没有书名、有没有页码。

OCR 内容验证看的是引用“是不是真的”。也就是回答中引用或概括的内容，是否能在对应 OCR 原文附近找到证据。

这个区别很关键。LLM 可能生成一个格式很漂亮的引用，比如“《某某》第 123 页”，但这页并没有对应内容。这种情况格式检查会通过，但内容验证能发现问题。

OCR 内容验证的价值是降低引用幻觉，尤其适合 deep 模式或高要求问题。代价是会增加一次额外验证调用和耗时，所以不一定每个 fast 请求都开启。

## 26. fast、standard、deep 三种性能模式分别牺牲和增强了什么？为什么不能所有请求都用 deep？

三种模式本质是在速度、成本和可靠性之间做取舍。

fast 模式更关注响应速度。它检索数量少，上下文预算小，通常不开启复杂的段落双路检索、混合检索、OCR 引用验证和恢复循环。适合快速探索或普通问题。

standard 模式是默认平衡方案。它会保留必要的检索质量控制，比如基础 CRAG，但不会把所有高成本环节都打开。

deep 模式面向高可信回答。它会使用更多检索结果、更大上下文、混合检索、多查询分解、引用 OCR 验证和恢复循环。适合复杂理论分析、严格引文定位和研究型问题。

不能所有请求都用 deep，原因是：

- 延迟更高。
- LLM 和 embedding 成本更高。
- 检索和验证链路更复杂。
- 简单问题没必要用重流程。

所以性能模式是产品化设计：让用户或系统根据问题难度选择合适成本。

## 27. 如果用户问“《关于费尔巴哈的提纲》在哪一卷哪一页”，系统应该如何走链路？

这是典型书目查找问题。

系统首先通过意图识别判断为 bibliographic lookup，而不是普通 RAG 问答。接着从 query 中识别篇名“关于费尔巴哈的提纲”，通过 WorkCatalog 或 article locator 找到对应 work_id 和不同版本信息。

如果用户没有指定版本，系统会按默认版本优先级返回更权威版本，比如优先《全集》。如果用户指定“文集”或“选集”，则返回对应版本。

这类问题不应该主要依赖向量检索，因为答案来自结构化目录和页码元数据。向量检索最多作为补充验证。

最终回答应该给出：

- 篇名。
- 所在版本。
- 来源文件或卷册。
- 起止页码。
- 必要时说明不同版本页码不同。

## 28. 如果用户问“异化劳动是什么意思”，系统和“精确引文定位”类问题的处理方式有什么不同？

“异化劳动是什么意思”属于概念解释，重点是理解和综合，不是找某一句原文的出处。

系统会识别为 concept explain 或 theory analysis，然后围绕“异化劳动”构建查询和主题约束，检索多个相关段落。检索时更需要上下文完整性，可能会使用父段落窗口扩展或段落级检索。

生成回答时，prompt 会要求结合原文证据解释概念，而不是只返回某个页码。

精确引文定位则不同。用户给出一段话问“出自哪里”，系统要优先使用 BM25、exact quote lookup、OCR 原文匹配和页码验证。它追求的是定位准确，而不是概念综合。

简单说：

- 概念解释重在“多证据综合解释”。
- 引文定位重在“字面匹配和出处精确”。

## 29. 如果线上出现“回答看起来对，但引用页码错了”，你会从哪些环节排查？

我会按数据链路和生成链路逐层排查。

第一，看原始 OCR 页面的 `pdf_page` 和 `printed_page` 是否正确。如果 OCR 页面本身页码识别错了，后面都会错。

第二，看 `page_map.json` 是否覆盖了该卷册，该 PDF 到印刷页码映射是否准确。

第三，看 paragraph cache 中该段落的 source、pdf_page、printed_page、citation_page 是否一致。

第四，看向量库 metadata 是否保留了正确页码字段。有时缓存正确，但构建向量库时字段丢失或写错。

第五，看检索结果 evidence card 中的页码是否正确。如果这里已经错了，问题在检索或元数据。

第六，看 LLM 生成时是否篡改或混用了页码。如果 evidence card 正确但回答错了，说明生成层或引用格式修复层需要加强约束。

第七，看引用审计和 OCR 验证是否开启，以及为什么没有拦住错误。

这个问题不能只看最终回答，必须沿着 OCR、page map、paragraph cache、vector metadata、evidence card、generation、citation audit 全链路查。

## 30. 如果要把 MarxOS 做成企业级或研究机构可用的产品，你会继续补哪些能力？

我会从数据、检索、生成、评测和运维五个方向升级。

数据层：

- 支持增量 OCR 和增量索引。
- 对不同版本语料做版本管理。
- 完善页码映射和篇目元数据审核流程。
- 对 OCR 质量建立自动评分。

检索层：

- 引入 cross-encoder reranker，提高 top-k 排序质量。
- 增强 HyDE 或多查询扩展。
- 支持更细粒度的元数据过滤和用户指定版本。
- 优化 Milvus 服务化部署。

生成层：

- 支持 token 级流式输出。
- 增强多轮上下文管理。
- 对高风险引用问题强制 citation verification。
- 加入更严格的拒答策略，避免无证据回答。

评测层：

- 建立覆盖书目、引文、概念、比较、深度分析的自动评测集。
- 持续统计 work_correct、page_correct、citation_accuracy、answer_quality。
- 做回归门禁，防止新版本破坏旧能力。

运维层：

- 增加监控、告警、日志追踪。
- 接入 Phoenix/OpenTelemetry 观察 LLM 调用链路。
- 加权限管理和用户隔离。
- 管理 LLM 成本、超时和降级策略。

最终目标是把它从个人研究型 RAG 系统，升级成可维护、可评测、可审计的学术知识服务平台。
